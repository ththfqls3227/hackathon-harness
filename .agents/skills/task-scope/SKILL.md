# 문제와 범위

하네스 [AGENTS.md](../../../AGENTS.md)와 [응시 규정](../../../docs/exam-contract.md), 실제 과제의 README·제공 자료·기존 코드를 먼저 읽는다. 이 스킬은 문제의 답이나 기술 스택을 미리 지정하지 않는다.

1. 사용자, 현재 업무 흐름, 실패 지점, 바꾸려는 결과를 한 문단으로 정리한다. 필수 산출물의 파일명·경로·형식·평가 기준을 원문과 대조한다.
2. 제공 데이터의 컬럼, 표본, 결측, 단위, 시간 범위를 로컬에서 확인한다. 데이터에 없는 KPI나 절감률을 약속하지 않는다. 데이터 분석 과제라면 앱 없이 분석 결과로 충분한지도 검토한다.
3. 답에 따라 구현이 달라지는 질문만 업무 담당자에게 묻는다. 우선순위, 예외 처리, 성공 기준 중 가장 큰 불확실성부터 묻는다. 참가자가 플랫폼 메신저로 직접 전달할 짧은 문장을 제시한다. 전달·응답을 관찰하지 않았으면 답변을 받았다고 쓰지 않는다.
4. 작은 해결책과 더 큰 해결책을 포함해 유효한 대안 2~3개를 비교한다. 사용자 가치, 제공 자료 적합성, 남은 시간, 검증 가능성으로 고른다. 복잡한 점수표가 필요하지 않으면 만들지 않는다.
5. 문제 정의 자체의 가정을 한 번 반박해 본다. 예를 들어 '새 화면이 필요한가, 기존 파일의 누락 탐지가 먼저인가?'를 확인한다. 이미 근거가 충분한 결정을 계속 뒤집지 않는다.
6. 최소 범위, 제외 범위, 성공을 관찰할 방법을 정한다. 필수조건 충돌이나 되돌리기 어려운 업무 결정은 사람의 답을 기다린다. 나머지는 가정을 표시하고 진행한다.

파일에서 알아낼 수 있는 사실은 먼저 직접 확인한다. 사람에게는 우선순위·예외의 업무 의미·트레이드오프처럼 판단이 필요한 것을 묻는다. 다른 답을 전제로 하는 질문은 그 답이 나온 뒤 묻고, 아직 답이 없는 내용을 결정된 것으로 취급하지 않는다. 질문은 현재 최소 범위를 바꿀 만큼 중요한 것부터 다룬다.

출력은 짧은 문제 정의, 출처 있는 필수조건, 핵심 질문, 대안과 선택 이유, 검증 가능한 최소 범위다. 과제에서 요구하지 않으면 별도 PRD를 추가하지 않는다. 범위가 정해지면 더 묻기보다 구현을 시작한다.
