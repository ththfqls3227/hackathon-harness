# 동작과 제출물 검증

작성자의 완료 요약만 믿지 말고 과제 README의 요구사항과 산출물을 직접 대조한다.

1. 필수조건별로 대응 파일, 확인 방법, 실제 결과를 연결한다. 파일 존재만으로 기능 완료를 판단하지 않는다.
2. 기존 프로젝트 명령을 사용해 바뀐 기능의 테스트를 실행한다. 그 명령의 대상 파일·설정·테스트 연결을 읽어 실제 변경 부분을 검사하는지 확인한다. 테스트 0개 또는 무관한 테스트의 통과는 해당 변경의 증거가 아니다. 타입·린트·빌드가 제공되어 있고 변경과 관련 있으면 실행한다. 도구가 없거나 실행 실패 시 범위와 원인을 기록하고 다음으로 작은 확인을 시도한다.
3. 경계면을 확인한다. API 필드와 화면이 읽는 필드, CSV 단위와 계산식, 결측값과 오류 처리, 저장 경로와 실제 읽는 경로를 함께 본다. 분석 결과는 표본 몇 건을 별도 계산해 대조하고 인과효과나 성능 개선을 근거 없이 주장하지 않는다.
4. 웹 서비스라면 프로세스·응답·실제 포트·바인딩을 확인한다. 브라우저 확인은 참가자가 플랫폼의 미리보기에서 직접 수행한다. HTTP 성공을 화면 조작 성공으로 바꾸어 쓰지 않는다. Computer Use·Playwright·브라우저 MCP를 통한 자동 조작을 하지 않는다.
5. 검토 역할을 분리할 수 있으면 `../../../roles/reviewer.md`를 사용한다. 지원이 없으면 별도 검토 패스로 수행하고 '단독 재검토'라고 기록한다. 작성자가 만든 테스트만으로 모든 요구 충족을 단정하지 않는다.
6. 실패한 필수조건은 우선 수정하고 해당 조건을 다시 검증한다. 최종 수정 이후 실행한 결과를 사용하며, 이전 버전의 성공 로그를 현재 버전의 증거로 쓰지 않는다. 예상대로 될 것이라는 판단과 실행 성공을 구분한다. 선택 기능 때문에 제출 시간을 놓치지 않는다.
7. 지정 파일명·경로·실행 설명·저장 상태·검증 결과·남은 한계를 확인한다. 제출 미리보기와 최종 완료는 참가자가 확인한다. 작업 완료, 제출물 확정, 최종 제출 완료를 서로 다른 상태로 보고한다.

최종 보고에는 해결한 문제, 동작 범위, 실행한 검증과 결과, 미확인·미완료 사항을 간결하게 쓴다. 실제 제출 완료는 참가자의 확인이나 허용된 플랫폼 증거가 있을 때만 쓴다. AI 금지 단계가 시작되면 검증·기록·답안 작성도 멈춘다.

## 조건이 있어야 실행되는 경로

오류 처리, 대체 경로, 재시도, 빈 데이터, 임계값 등 변경한 분기가 있으면 그 조건을 만드는 입력이나 로컬 대역을 사용해 실제로 실행한다. 조건에 도달한 증거와 기대한 결과를 함께 읽는다. 정상 입력의 전체 테스트 통과만으로 이 분기까지 검증됐다고 쓰지 않는다.

예를 들어 잘못된 CSV 열 수의 처리를 바꿨다면 열 수가 맞지 않는 입력으로 종료 코드와 보고서를 확인한다. 허용된 방법으로 조건을 만들 수 없으면 미확인 이유를 남긴다. 검증 때문에 외부 장애를 일으키거나 금지된 서비스·브라우저 자동화를 사용하지 않는다.
