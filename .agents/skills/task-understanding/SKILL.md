# 작성 항목과 구현 이해

하네스 [AGENTS.md](../../../AGENTS.md)와 [응시 규정](../../../docs/exam-contract.md)을 먼저 읽는다. **현재 단계가 작업 중이고 해당 AI 사용이 허용될 때** 적용한다. 제출물 확정·후속 준비·AI 금지 단계에서는 질문, 힌트, 설명 교정, 문서 작성까지 멈춘다. 미리보기 중이면 참가자가 작업 화면으로 돌아왔는지 확인한다.

## 작성할 항목부터 찾기

1. 실제 과제 README, 연결된 로컬 지침, 필수 산출물 목록에서 작성 항목을 모두 찾는다. 개수·문항·출력 파일명을 미리 정하지 않는다. 화면에만 있는 항목은 참가자가 허용 범위 안에서 전달한 텍스트로 확인한다. 접근하지 못한 화면의 항목까지 찾았다고 하지 않으며, 캡처·업로드·메신저 자동화를 요청하지 않는다.
2. 항목마다 **출처 / 작성·사용 단계와 AI 허용 근거 / 위치·형식·분량 / 상태 / 구현·검증 근거**를 연결한다. 플랫폼 입력칸도 파일 산출물과 별도로 포함한다. 형식이나 제한이 안내되지 않았다면 만들어내지 않는다. 허용 여부가 불명확한 항목만 보류하고 독립적인 작업을 계속한다.
3. 작업 중 AI 작성이 허용된 필수 답변·문서는 실제로 작성·갱신한다. '서술형'이라는 이름만으로 개발 중 필수 문서를 차단하지 않는다. 반대로 미래 후속 문항의 답안을 미리 만들어 두는 용도로 바꾸지 않는다. 플랫폼 입력은 참가자가 직접 하며 초안 작성·파일 저장·화면 입력·제출 완료를 구분한다.
4. 기존 필수 문서를 우선하고 필요할 때만 [근거 양식](../../../templates/work-evidence.md)의 작성 항목 표를 쓴다. 작업 결과는 실제 과제 공간에 두며 공개 하네스 clone 안에 쓰거나 외부로 전송하지 않는다.

## 질문에 사용할 근거

현재 세션에서 보이는 대화와 과제 공간 안에 이미 있는 허용된 CLI 대화·명령 로그, 작성 항목, 최신 코드, 실제 실행 결과를 연결한다. 전체 로그를 복제·색인하지 않고 관련 발언·명령·파일 위치만 필요한 만큼 읽는다. 개인 PC·홈 디렉터리의 CLI 저장소, 전역 대화·메모리, 인증 파일, 다른 프로젝트는 검색하지 않는다. 로그를 볼 수 없으면 그 한계를 밝히고 현재 대화·코드·문서부터 사용한다.

- **발언의 주체와 실행 여부:** 참가자가 제안·선택·수정한 내용, AI의 제안, 실제 실행 결과를 구분한다. AI가 제안했다는 이유로 구현되었거나 참가자가 이해했다고 기록하지 않는다.
- **불일치와 변경:** 문서의 주장과 코드, 계획과 구현, 검증 로그와 현재 버전, 사용자 설명과 실제 동작이 다른 부분을 우선한다. 계획했던 기능·과거 성공·대리지표를 현재 구현·검증·실측 효과로 바꾸지 않는다.
- **출제 방식의 한계:** 재응시 가이드는 확정된 제출물과 작업 기록을 기반으로 후속 질문을 생성한다고 안내한다. 이 스킬은 같은 종류의 근거로 이해를 점검하지만, 실제 생성 알고리즘·문항·채점 기준·점수를 안다고 주장하지 않는다. 여기서 만든 질문은 개발 중의 연습 질문이다.

## 판단 기록이 없을 때

허용된 개발 단계라면 지금의 실제 검토부터 함께 시작한다. 현재 코드·AI 제안에서 요구사항과 연결되는 선택 하나를 골라 근거와 대안·영향을 짧게 보여 주고, 참가자에게 유지·수정·보류 중 판단과 이유를 묻는다. 이미 기록에 답이 있으면 다시 묻지 않는다. 답에 의존하지 않는 작업은 계속한다.

선택을 받으면 필요한 변경을 수행하고 바뀐 동작을 검증한다. 변경이 필요 없으면 유지 이유와 확인 근거를 남긴다. 설명거리를 만들려고 불필요한 수정을 하지 않는다. **지금 새로 판단한 사실**과 **과거에 실제로 했다고 확인되는 사실**을 구분하며, 과거 이유를 소급해 만들어 쓰지 않는다. 참가자가 직접 고친 코드, 참가자의 지시를 AI가 구현한 변경, AI가 독자적으로 고친 부분도 구별한다. 응답이 없으면 판단 미확인으로 남기며 AI가 참가자의 선택을 대신 만들어 기록하지 않는다. 제출 확정 이후에는 이 과정도 시작하거나 이어가지 않는다.

## 개발 중 짧은 이해 점검

중요한 결정이나 기능 구현·검증이 끝났을 때 **1~2개씩** 묻는다. 모든 도구 호출·사소한 수정마다 묻거나 미응답 질문을 계속 쌓지 않는다. 선택 이유와 실제 동작을 본인의 말로 연결하게 하고, 첫 답변 전에 모범 답안을 붙이지 않는다. 필수 문서 초안 작성과 이해 점검은 다른 작업이다.

질문은 해당 근거에서 파생하고 아래 관점 중 중요한 것만 고른다. 일반 기술 상식 퀴즈나 실제 시험의 특정 주제를 미리 넣지 않는다.

| 점검할 부분 | 질문을 만드는 기준 |
|---|---|
| 문제와 구현의 연결 | 사용자의 어떤 어려움을 해결하려 했는가 → 선택한 방법 → 실제 코드의 입력·처리·출력 → 확인된 결과가 연결되는가 |
| 작동 원리 | 실제 입력 한 건이 어떤 처리·저장·출력을 거치는가 |
| 목적·가정·제약 | 무엇을 개선하려고 했고 어떤 가정이 바뀌면 결과가 달라지는가 |
| 선택·대안 | 왜 이 방법을 골랐고 무엇을 포기했는가. 참가자가 바꾼 AI 제안이 있다면 이유는 무엇인가 |
| AI 협업에서의 판단 | 원래 AI 제안 → 발견한 문제·빠진 조건 → 참가자의 실제 판단 → 유지·수정한 부분 → 검증 결과를 설명하는가. 제안과 실제 변경, 사람과 AI의 기여를 구분하는가 |
| 보장과 측정 | 구현이 보장하는 범위는 어디까지인가. 추정·대리지표와 실제 측정을 구별하는가 |
| 오류·한계 | 어떤 입력에서 실패·누락·기본값이 생기는가. 구현하지 않은 부분의 영향은 무엇인가 |
| 검증과 반례 | 어떤 실행이 주장을 뒷받침하며 어떤 반례는 아직 검사하지 않았는가 |

참가자가 답하면 **맞게 설명한 부분 → 빠진 연결·오해 → 코드·문서·실행 근거 → 필요한 재질문 한 개** 순서로 짧게 피드백한다. 이해가 불분명한 부분은 작은 입력을 따라가게 한다. 실제 발언 없이 답이나 참가자의 판단 이유를 만들어 쓰지 않는다.

상태는 `질문 전 / 응답 대기 / 재확인 필요 / 해당 설명 확인`으로 구분한다. 침묵·'알겠어'·AI 작성 문서만으로 확인 완료로 바꾸지 않는다. 근거가 불충분하면 오답으로 단정하지 않는다. 관련 구현이나 결정이 바뀌면 해당 설명만 다시 대조한다. 전체 이해도 점수는 만들지 않는다.

답을 기다리는 동안 독립적인 구현·검증은 이어간다. 사용자의 답이 실제 요구사항·업무 기준을 바꾸는 경우에만 의존하는 변경을 보류한다. 이해 점검을 새 승인 절차나 제출 자격 조건으로 만들지 않는다.

## 제출 전 종합 점검

**제출물 확정 전에**, 현재 코드·작성 항목·대화의 결정·최종 검증을 다시 대조한다. 문서의 누락·오래된 주장·미구현을 먼저 정리하고 [task-verify](../task-verify/SKILL.md)로 실제 산출물을 확인한다. 이미 검증한 동일 버전의 명령을 질문 때문에 반복 실행할 필요는 없다.

그다음 전체 흐름·핵심 선택·한계·검증을 연결하는 **3~5개 질문**을 한 번에 제시하되 남은 시간에 맞춰 줄인다. 이전에 잘못 설명했거나 아직 답하지 않은 핵심 항목을 우선하고, 이미 확인한 설명을 그대로 반복하지 않는다. 필수 파일 저장과 제출 여유를 먼저 확보하며 질문을 다 답할 때까지 제출을 막지 않는다.

문제에서 구현·검증까지의 연결과 실제 AI 협업 판단을 우선 점검한다. 사용한 라이브러리 이름이나 'AI가 만들어 줬다'는 설명에서 끝나면 관련 코드와 구체적인 선택 하나를 연결하도록 묻는다. 수정 이력이 없으면 유지 판단 또는 기록 미확인을 사실대로 다루고 사례를 지어내지 않는다.

필요한 기록은 `작성 항목 상태 / 근거와 대상 버전 / 질문과 실제 설명의 요지 / 이해 상태 / 다음 확인` 정도다. 긴 로그나 미래 답안집을 만들지 않는다. 제출물 확정이 알려지면 미응답이 남아도 **추가 질문·채점·힌트·윤문 없이 종료**한다.
