# 실행 흐름

하네스 루트의 [AGENTS.md](../../../AGENTS.md)와 [응시 규정](../../../docs/exam-contract.md)을 먼저 읽는다. 이 파일 기준 루트는 `../../..`이다. 모든 산출물은 실제 과제 작업 공간에 작성하고 하네스를 과제 정답으로 대체하지 않는다.

## 시작과 시간

- 실제 과제 README·지침·기존 코드와 남은 시간을 확인한다. 실행 방법과 필수 제출물을 추출한다. 모델은 플랫폼에서 허용된 목록 중 선택하며 모델 식별자를 추측하거나 업데이트하지 않는다.
- 현재 디렉터리와 실제 과제 루트를 확인한다. 준비 프로필의 시작 항목을 짧게 정리하고, 승인 대기·실행 중·완료 상태를 구분한다. 안내가 없는 항목을 기능 사용 가능으로 해석하지 않는다.
- 런타임·패키지 매니저·테스트 명령을 확인한다. 기존 테스트가 있으면 현재 상태를 확인하고 기존 실패와 변경에 따른 실패를 구별한다.
- 낯선 코드에서는 바꿀 흐름의 입력 지점 → 처리 → 저장·출력 → 관련 테스트를 실제 경로로 짧게 연결한다. 기존 파일 목록·검색 도구를 사용하고, 요약에 없는 파일이나 호출자가 없다고 단정하지 않는다. 전역 검색기나 별도 색인 설치는 필요하지 않다.
- 필요하면 `../task-scope/SKILL.md`를 읽는다. 질문 대기 중에는 파일 구조와 데이터를 확인하는 등 답과 독립적인 일을 진행한다.
- 제출에 필요한 시간을 먼저 확보하고 남은 시간을 맥락·범위 확인, 핵심 구현, 검증·수정, 문서 정리에 나눈다. 핵심 구현과 검증에 가장 많은 시간을 쓰되 실제 남은 시간과 운영 공지를 기준으로 조정한다. 절대 마감과 후속 단계 시간을 별도로 확인한다.

## 변경 크기에 맞춘 진행

오타·문구·명확한 한 곳의 수정은 바로 고치고 필요한 확인만 한다. 새 기능이나 여러 파일에 걸친 변경은 아래 순서로 진행하되 기존 과제 문서에 짧게 합친다. 단계마다 새 문서나 사용자 승인을 요구하지 않는다.

| 단계 | 다음 단계로 넘어갈 근거 |
|---|---|
| 계획 | 변경 파일, 선행 조건, 제외 범위, 관찰 가능한 성공·실패 조건 |
| 사전 검토 | 실제 호출자·입출력·검증 명령과 계획을 대조. 필수조건 충돌은 수정하거나 근거로 해소 |
| 구현 | 검토한 범위의 작은 동작 완성. 새 업무 판단이 필요하면 그 부분만 확인 |
| 검증 | 변경된 경로를 실제로 실행하고 결과 확인. 실패하면 원인을 바꿀 증거를 읽고 수정 |
| 정리 | 확인된 결과·남은 한계·저장 상태 전달. 제한시간 종료를 성공으로 바꾸지 않음 |

사전 검토는 지원·허용되는 검토자에게 맡기거나 단독 재검토로 수행한다. 지적마다 수정, 근거 있는 반박, 선택 사항 보류를 구분하고 수정 후에는 기존 문제와 수정으로 생길 수 있는 영향부터 재확인한다. 같은 실패가 반복되는데 새 근거가 없다면 패치를 멈추고 원인·범위·남은 시간을 다시 판단한다.

이 순서는 Codex가 따르는 작업 지침이다. 단계 전환을 강제하는 플러그인·hooks·상태 머신이 설치된 것이 아니다.

## 구현

1. 입력에서 결과까지 가장 작은 흐름을 먼저 완성한다. 과제 종류에 따라 분석 노트북, CLI, 보고서, 웹 서비스 중 적합한 형태를 선택한다.
2. 기능 하나를 붙이면 그 기능의 실제 입력·출력을 검증한다. 기존 테스트 경계가 있으면 재사용하고, 새 테스트는 사용자가 관찰하는 동작을 확인한다. 기대값은 구현식을 복제해서 만들지 말고 요구사항이나 독립 계산에서 얻는다. 오류가 나면 재현 → 원인 가설 → 최소 수정 → 같은 재현 조건 재검증 순서로 진행한다. 여러 가설의 수정을 한꺼번에 섞지 않는다.
3. 외부 도구가 필요하면 기능 공백과 데이터 흐름부터 확인한다. 공개 Skill·MCP·Plugin의 허용된 다운로드와 문제·작업 결과의 외부 전송을 구분하고 응시 규정의 도구 기준을 적용한다. 외부 AI 호출·원격 저장·자동 브라우저 조작이 필요한 도구는 이 제한 환경의 해법으로 삼지 않는다. 기본 MCP는 설치하지 않는다.
4. 독립 작업과 지원되는 native subagent가 있고 규정상 허용될 때만 위임한다. 요청에는 목표, 최소 맥락, 담당 파일, 현재 단계·응시 규정·허용 모델, 검증 기준을 담는다. 공통 파일을 동시에 고치지 않는다. 응답 대기와 병합 비용이 더 크면 혼자 진행한다.
5. 중요한 선택을 했을 때 실제 근거를 필수 문서 또는 `../../../templates/work-evidence.md` 형식에 짧게 기록한다. 사후에 수행하지 않은 검증이나 대화를 만들어 채우지 않는다.

## 검증과 종료

`../task-verify/SKILL.md`로 요구사항과 동작을 대조한다. 시간이 부족하면 선택 기능부터 덜고 필수 기능·오류 수정·제출 확인을 우선한다. 플랫폼 오류는 증상과 시각을 남겨 참가자가 공식 신고 경로로 전달한다. 같은 실패를 이유 없이 반복하거나 차단을 우회하지 않는다.

필수 산출물과 검증 근거가 준비되면 참가자에게 저장·제출 확인 사항을 전달한다. 미리보기, 제출물 확정, 후속 준비, 최종 완료를 구분한다. 제출물 확정부터 과제 AI 작업을 중단하며, 대기 중 추가 수정·후속 답안 준비·제출 자동 조작을 수행하지 않는다.

## 중단 후 재개

대화가 압축되거나 작업이 끊길 때는 기존 과제 문서 또는 근거 양식의 재개 항목에 현재 단계, 변경 파일, 마지막 실행 결과와 대상 버전, 남은 문제, 다음 한 가지 행동을 적는다. 이 기록은 과제 공간 안에만 둔다.

재개 시 그 기록이 가리키는 실제 파일·로그를 열고 현재 변경과 대조한다. 기록 이후 파일이 바뀌었거나 실행 대상을 확인할 수 없으면 관련 검증을 다시 한다. 요약의 '완료' 한 줄은 증거가 아니다. 먼저 과제 안의 기록을 찾아보고 빠진 업무 판단만 묻는다. 개인 PC의 과거 대화·전역 메모리·다른 프로젝트를 가져오거나 검색하지 않는다.

## 연습 시나리오

- 정상: 제공 CSV의 오류를 찾는 과제에서 스키마 확인 → 오류 기준 확인 → 작은 검사기 구현 → 정상·오류 입력 검증 → 지정 파일 저장까지 진행한다.
- 실패: 스킬 자동 인식이나 subagent가 없으면 파일을 명시적으로 읽고 단독으로 이어간다. 환경 업데이트로 해결하지 않는다.
- 경계: 공개 저장소 push나 외부 모델 사용이 제안되면 해당 동작을 중단하고 로컬 검증과 허용된 작업을 이어간다.
